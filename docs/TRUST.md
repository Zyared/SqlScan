# Как проверить баллы и точность SqlScan 2.0.1

## Демонстрация за три минуты

1. Откройте «Проверка баллов SqlScan» из меню «Пуск» или запустите `Check-Scores.cmd` из комплекта. Сценарий работает локально. При каждом запуске он генерирует новую тысячу строк и проверяет ещё 34 контрольных примера.
2. В открывшейся таблице сопоставьте вход, ожидаемый балл и ответ установленного EXE. Ожидание вычисляет отдельная программа на Python. Она читает веса из опубликованной схемы и считает вхождения регулярным выражением с учётом перекрытий. SqlScan написан на C++ и реализует собственный поиск. Проверяются сумма, количество совпадений, итог построчного решения и уровень риска. Сам проверяющий сценарий обязан заметить четыре намеренные подмены результата.
3. Предложите собственный нейтральный текст, запишите прогноз на бумаге, введите текст на вкладке «Проверка» и нажмите «Проверить». Раскройте расчёт в отчёте. При исходных правилах точка с запятой весит один балл, порог одной строки равен пяти. Для сравнения ниже приведены результаты, которые можно пересчитать в уме.

| Введено | Расчёт | Решение |
|---|---|---|
| Четыре знака `;;;;` | 4 × 1 = 4 | Ниже порога |
| Пять знаков `;;;;;` | 5 × 1 = 5 | Достигнут порог |
| Три знака `;;;` на первой строке, два на второй | 3 + 2 = 5 в документе | Обе строки ниже порога |
| Два дефиса `--` | 1 × 3 = 3 | У правила установлен флаг высокого риска |
| Три дефиса `---` | 2 × 3 = 6 | Два перекрывающихся совпадения |

Баллы выражают сумму назначенных весов. Вероятностная калибровка весов не проводилась. Если преподаватель изменил вес или порог в своей БД, расчёт в окне использует эти настройки. Контрольный пакетный прогон использует заводской набор. Исходные записи для проверки и алгоритм подсчёта доступны для просмотра. [Правила](../db/schema.sql) · [Независимый пересчёт](../tests/score_audit.py)

HTML и JSON каждого запуска сохраняются в отдельном каталоге `%LOCALAPPDATA%\SqlScan2\Checks`. В отчёте записаны SHA-256 проверенного EXE и число, определяющее случайную выборку. Для повтора откройте PowerShell в каталоге установленного комплекта, подставьте это число вместо 20261119 и укажите доступный для записи путь вывода.

```powershell
.\validation\python\python.exe -B .\source\tests\score_audit.py . "$env:TEMP\scores.json" --seed 20261119 --html "$env:TEMP\scores.html"
```

## Как измерено качество обнаружения

Разметку для двух основных наборов предоставили их авторы. На каждом входе запускаются SqlScan 2.0.1, исходный движок 1.0, libinjection и OWASP CRS 942 на Coraza. Все четыре получают одно и то же значение. Сценарий удерживает эталонные метки у себя, передаёт движкам только текст и сверяет порядок возвращённых записей. Сопоставление с разметкой выполняется после получения вердиктов. Версии файлов, способы извлечения записей и их контрольные суммы опубликованы. [Опись источников](../benchmark/sources.json) · [Сценарий измерения](../benchmark/verify_quality.py)

| Размеченный набор | Записей | Найдено атак (TP) | Ложные тревоги (FP) | Верно признано чистыми (TN) | Пропущено атак (FN) | Точность тревог | Полнота |
|---|---:|---:|---:|---:|---:|---:|---:|
| HttpParams | 10 051 | 2 028 | 1 | 6 433 | 1 589 | 99,95 % | 56,07 % |
| Kaggle SQL Injection Dataset | 30 919 | 4 512 | 596 | 18 941 | 6 870 | 88,33 % | 39,64 % |

Точность тревог равна TP / (TP + FP). Полнота равна TP / (TP + FN). Например, на Kaggle из 5 108 тревог 4 512 совпали с разметкой. Из всех 11 382 записей с меткой атаки обнаружены те же 4 512. По этим двум отношениям преподаватель может проверить оба процента обычным калькулятором.

| Движок | F1 на HttpParams | F1 на Kaggle |
|---|---:|---:|
| SqlScan 1.0 | 0,718385 | 0,547043 |
| SqlScan 2.0.1 | 0,718385 | 0,547241 |
| libinjection 4.0.2 | 0,984131 | 0,722688 |
| OWASP CRS 4.25.0, группа 942 | 0,999308 | 0,714630 |

Критерий ТЗ «F1 версии 2.0 не хуже 1.0 на том же наборе» выполнен на обоих наборах. На HttpParams у SqlScan одна ложная тревога в группе пунктуации и разметки. На Kaggle все 596 ложных тревог содержат SQL-лексику согласно объявленному классификатору. Это показывает риск тревог на обычных технических записях. Восемь тематических срезов показывают неодинаковую полноту. Например, в двух небольших срезах SecLists обнаружены 2 записи из 52 и 0 из 8. Полные результаты содержат объёмы всех групп, включая пропуски. [Агрегаты по движкам и классам](../benchmark/results/release-quality.json)

Всего обработано 102 863 записи из пяти источников. Возможны повторы как внутри наборов, так и между ними. В 36 000 нормальных запросов CSIC SqlScan дал ноль тревог. В 25 065 разнотипных аномальных запросов он выдал 2 032 тревоги. По меткам последнего набора нельзя определить полноту именно для SQL-инъекций. Для оценки работы на журналах конкретной системы нужна отдельная разметка этих журналов.

## Повтор эксперимента

В каталоге программы выполните `Recheck.cmd -Quality -Cache D:\SqlScan-test-data`. Первый запуск получает открытые данные по зафиксированным адресам и проверяет хеши. Повтор с полным кэшем работает автономно. По окончании откройте напечатанный каталог результатов. При несовпадении агрегатов с опубликованным JSON сценарий завершится ошибкой. [Матрица приёмки](VERIFICATION.md)

Протокол составлен авторской стороной. Внешняя лабораторная сертификация отсутствует. Преподаватель может проверить арифметику на своей выборке, повторить измерение на опубликованных данных и сверить контрольную сумму своей сборки с протоколом. [Контрольный прогон баллов](../benchmark/results/score-audit.json)
